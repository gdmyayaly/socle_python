


Objectif

Mettre en place un mécanisme standard de contrôle d'unicité d'exécution des batchs TRPPU afin d'éviter l'exécution simultanée de plusieurs instances d'un même traitement.

User Story

En tant qu'exploitant TRPPU

Je souhaite qu'un batch vérifie qu'aucune autre instance du même traitement n'est déjà en cours d'exécution avant de démarrer

Afin d'éviter les exécutions concurrentes, les traitements en doublon et les incohérences de données.

Contexte

Les batchs TRPPU exécutés sous OpenShift peuvent être déclenchés :

par CronJob ;
manuellement ;
par relance d'exploitation.

Dans certaines situations exceptionnelles, plusieurs instances d'un même traitement pourraient être lancées simultanément.

Les batchs doivent donc implémenter un contrôle d'unicité standard reposant sur la table :

 
TRPPU_SUIVI_BATCH
 

Périmètre

Cette évolution concerne :

 
YB05
YB06
YB07
et devra être réutilisable pour tous les futurs batchs TRPPU.

Principe

Avant toute exécution métier, le batch doit rechercher dans :

 
TRPPU_SUIVI_BATCH
une exécution du même batch avec le statut :

 
EN_COURS

Cas 1 : aucune exécution active

Le traitement démarre normalement.

Une ligne est créée :

 
STATUT = EN_COURS
DATE_DEBUT = NOW()

Cas 2 : une exécution active existe

Si :

 
STATUT = EN_COURS
et que :

 
DATE_DEBUT + TIMEOUT_BATCH > NOW()
alors l'instance est considérée comme active.

Le batch :

journalise l'information ;
s'arrête immédiatement ;
n'exécute aucun traitement métier.

Message attendu :

 
Une instance du batch YB07 est déjà en cours d'exécution.
 
Le démarrage est refusé.

Cas 3 : exécution abandonnée

Si :

 
STATUT = EN_COURS
mais que :

 
DATE_DEBUT + TIMEOUT_BATCH < NOW()
alors l'exécution précédente est considérée abandonnée.

Le batch doit :

Étape 1

Mettre à jour la ligne existante :

 
STATUT = ABANDONNE
DATE_FIN = NOW()

Étape 2

Renseigner le commentaire :

 
Exécution considérée abandonnée suite dépassement du timeout d'exécution.

Étape 3

Tracer l'opération dans Kibana.

Étape 4

Autoriser la nouvelle exécution.

Source du timeout

Le timeout utilisé pour déterminer qu'un batch est abandonné doit être aligné sur le timeout configuré pour le POD OpenShift correspondant.

Exemple :

 
YB05 → timeout POD YB05
YB06 → timeout POD YB06
YB07 → timeout POD YB07

Fin d'exécution
Succès

 
STATUT = SUCCES
DATE_FIN = NOW()

Échec

 
STATUT = ECHEC
DATE_FIN = NOW()

Journalisation

Toutes les décisions prises doivent être tracées :

Dans Kibana
détection d'une instance active ;
détection d'une instance abandonnée ;
démarrage autorisé ;
démarrage refusé.
Dans TRPPU_SUIVI_BATCH

par l'utilisation des statuts :

 
EN_COURS
SUCCES
ECHEC
ABANDONNE

Critères d'acceptation
CA-01

Étant donné qu'aucune instance du batch n'est en cours,

Quand le batch démarre,

Alors une ligne est créée avec :

 
STATUT = EN_COURS
et le traitement démarre.

CA-02

Étant donné qu'une instance du même batch est encore active,

Quand une nouvelle instance démarre,

Alors elle s'arrête immédiatement sans exécuter de traitement métier.

CA-03

Étant donné qu'une instance est restée :

 
EN_COURS
au-delà du timeout autorisé,

Quand une nouvelle instance démarre,

Alors l'ancienne exécution est marquée :

 
ABANDONNE
et la nouvelle instance est autorisée à démarrer.

CA-04

Les batchs :

 
YB05
YB06
YB07
utilisent tous le même mécanisme de contrôle d'unicité.
