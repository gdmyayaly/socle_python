========================================================================
YB07 - INITIALISATION DES CLES DE REPARTITION VIA HELM (KUBERNETES)
========================================================================

Objet : initialiser un referentiel de cles de repartition avec le
CronJob Helm de yb07, etape par etape, apres creation des tables.

Referentiel utilise dans les exemples : 1. Le remplacer partout si
besoin. Toutes les lignes du CSV doivent porter ce meme id_referentiel.


------------------------------------------------------------------------
1. REGLES A RESPECTER
------------------------------------------------------------------------

- Ne JAMAIS laisser "init" tourner sur un schedule (ex. */15) :
  init est une operation unique, certaines etapes durent des heures,
  et l'etape "cles" est IRREVERSIBLE (CA4 de DSR-699).
- Le CronJob reste SUSPENDU (suspend: true). Chaque etape est lancee
  a la main avec "kubectl create job --from=cronjob/...".
- Une etape a la fois. On ne passe a la suivante que si le rapport
  se termine par "RESULTAT : SUCCES" et que le pod est "Completed".
- Pas de relance automatique : backoffLimit: 0 si le chart le permet.
- Pas d'activeDeadlineSeconds trop court : il tuerait "migration" ou
  "cles" en plein milieu.


------------------------------------------------------------------------
2. VALUES.YAML DE BASE
------------------------------------------------------------------------

cronjobs:
  enabled: true
  jobs:
    yb07:
      schedule: "0 0 1 1 *"
      suspend: true
      concurrencyPolicy: Forbid
      successfulJobsHistoryLimit: 3
      failedJobsHistoryLimit: 3
      image:
        repository: fhgf
        tag: "1.0.0"
        pullPolicy: IfNotPresent
      command:
        - python
        - '-m'
        - app.main
        - db-check

Notes :
- "schedule" est sans importance tant que suspend vaut true.
- Preferer un tag fige a "latest" : on sait quelle version a tourne.
- Certificat de l'entreprise : S3_CA_BUNDLE=certif/cacert.pem (chemin
  relatif a la racine de yb07 dans l'image) ; le fichier doit etre
  present dans l'image ou monte en volume.
- Configuration (SGBD_*, S3_*, AWS_*, CSV_*) en variables
  d'environnement ; mots de passe dans un Secret (envFrom). Les
  variables du pod priment sur un eventuel .env.


------------------------------------------------------------------------
3. PROCEDURE POUR CHAQUE ETAPE
------------------------------------------------------------------------

a) Remplacer le bloc "command" du values.yaml par celui de l'etape
   (voir section 4), en gardant l'indentation de votre fichier.

b) Appliquer :

   helm upgrade <release> <chart> -f values.yaml

c) Lancer le job (nom unique a chaque fois) :

   kubectl create job yb07-<etape> --from=cronjob/<nom-du-cronjob>

d) Suivre le rapport :

   kubectl logs -f job/yb07-<etape>

e) Verifier la fin du rapport ("RESULTAT : SUCCES") et le statut :

   kubectl get job yb07-<etape>

f) Relancer une etape deja lancee : supprimer l'ancien job ou changer
   son nom (ex. yb07-chargement-2).

   kubectl delete job yb07-<etape>


------------------------------------------------------------------------
4. LES ETAPES, DANS L'ORDRE
------------------------------------------------------------------------

ETAPE 0a - Connexion MySQL                          duree : secondes
Rejouable : oui

      command:
        - python
        - '-m'
        - app.main
        - db-check

A verifier : lecture et ecriture "connected".


ETAPE 0b - Acces S3 et presence du CSV              duree : secondes
Rejouable : oui

      command:
        - python
        - '-m'
        - app.main
        - s3-check

A verifier : "Acces : ok", la ligne "tls" (bundle attendu), et le
fichier CSV visible dans le listing.
Pour lister un autre dossier : ajouter "- '--prefixe'" puis
"- <dossier>" a la fin de la liste.


ETAPE 1 - Marche a blanc                            duree : secondes
Rejouable : oui (n'ecrit rien)

      command:
        - python
        - '-m'
        - app.main
        - init
        - '1'
        - '--dry-run'

A verifier : les scripts sont lus et decoupes, aucune ecriture.


ETAPE 2 - Chargement du CSV                   duree : longue (22 M l.)
Rejouable : oui (TRUNCATE puis rechargement)

Mode strict (la premiere ligne non conforme arrete tout) :

      command:
        - python
        - '-m'
        - app.main
        - init
        - '1'
        - '--etape'
        - chargement

Mode tolerant (les lignes non conformes sont ecartees et listees
dans le rapport final) :

      command:
        - python
        - '-m'
        - app.main
        - init
        - '1'
        - '--etape'
        - chargement
        - '--skip-errors'

A verifier : LIGNES_CHARGEES, LIGNES_ACTIVES, et en mode tolerant
LIGNES_IGNOREES et la section "Avertissements :".
--skip-errors n'ecarte que les lignes incompletes (et les doublons).
Pour ecarter AUSSI les sites dont un total de trafic vaut 0 (sinon
division par zero a l'etape 7), ajouter "- '--all'" apres
"- '--skip-errors'" : voir SITES_TOTAL_NUL_ECARTES et les
avertissements "Site ... ecarte". --all seul est refuse.
ATTENTION : un PDI ecarte n'aura PAS de cle calculee a l'etape 7.
Faire valider la liste des lignes ecartees avant de continuer.

Purge : la table est videe par TRUNCATE (quasi instantane). Refuse si
la table contient un autre referentiel. Irreversible, exige le droit
DROP. Si l'API lit la table, le chargement echoue apres 60 s
(CHARGEMENT_LOCK_WAIT_TIMEOUT) au lieu de la bloquer : relancer.

Index : par defaut ils restent en place pendant le chargement
(insertion par lots, plus lent, mais aucune instruction longue
exposee a une coupure reseau). Un doublon de PDI est rejete a
l'insertion avec son numero de ligne. CHARGEMENT_RETIRER_INDEX=true
retire les index puis les reconstruit en une passe (plus rapide,
ALTER final de plusieurs minutes). Memoire du pod bornee (deux lots
de CHARGEMENT_TAILLE_LOT lignes).
Suivre l'avancement : lignes "Avancement chargement" (debit_lignes_s)
dans kubectl logs.

Fichier different de CSV_CLES_REPARTITION : ajouter a la liste
"- '--fichier'" puis "- <nom_du_fichier.csv>".

A verifier : CA1 (une cle par PDI actif), CA2, CA3 (sommes a 1).

------------------------------------------------------------------------
5. EN CAS D'ECHEC
------------------------------------------------------------------------

Si le rapport indique "REPRENDRE_PAR = finaliser-chargement" : le
fichier est entierement charge, seule la suite a echoue (index,
doublons, sites a total nul). Les donnees sont CONSERVEES. Reprendre
sans recharger, avec les memes options que le chargement :

      command:
        - python
        - '-m'
        - app.main
        - finaliser-chargement
        - '1'
        - '--skip-errors'
        - '--all'

puis reprendre la chaine : init 1 --depuis migration.

Sinon, le rapport indique "REPRENDRE_A = <etape>". Corriger la cause,
puis reprendre a cette etape et enchainer les suivantes :

      command:
        - python
        - '-m'
        - app.main
        - init
        - '1'
        - '--depuis'
        - <etape>

"--depuis cles" enchaine directement le calcul irreversible : ne
l'utiliser qu'apres avoir relu le rapport de l'etape "versions".

Codes de sortie : 0 = succes, 1 = echec (le job passe en Failed).


------------------------------------------------------------------------
6. PASSAGES SUIVANTS (NOUVEAU REFERENTIEL)
------------------------------------------------------------------------

Une fois les durees connues (ligne "Fin etape", champ duration_ms dans
les logs) et la fenetre d'exploitation validee, la chaine peut etre
lancee d'un bloc sur un NOUVEAU referentiel :

      command:
        - python
        - '-m'
        - app.main
        - init
        - '2'

Ajouter "- '--skip-errors'" pour le mode tolerant au chargement.

ATTENTION : la purge est un TRUNCATE, et le chargement refuse de
tourner si trppu_cles_repartition contient un autre referentiel. Tant
que le referentiel 1 y est charge, "init 2" est refuse des l'etape
chargement, sans rien ecrire. Vider la table (TRUNCATE manuel, apres
accord) avant de charger un nouveau referentiel.


------------------------------------------------------------------------
7. POINTS D'ATTENTION DEPLOIEMENT
------------------------------------------------------------------------

- yb07 n'a pas de .dockerignore et le Dockerfile fait "COPY . .".
  Un .env present au moment du build finit dans l'image, avec les
  mots de passe. Verifier l'image ou ajouter un .dockerignore.
- Le rapport part sur la sortie standard, les logs JSON sur la sortie
  d'erreur : les deux sont visibles dans "kubectl logs".
- Le dossier logs/ du conteneur disparait avec le pod : se fier a
  "kubectl logs" (ou Kibana si la collecte est en place).
- La table trppu_referentiel n'est plus consultee par yb07.
