En tant que TRPPU,

Je veux adapter la requête qui récupère les données de trafics de databricks 

Afin de prendre en compte la nouvelle structure des tables gold.

Les tables gold ne contiennent maintenant que les trafics utiles à TRPPU.

Tout ce qui concerne la hiérarchie d'un établissement avec tout ses rattachements fonctionnels sont sortis dans une table dimension dédiée "ppd_dd_kairos_int.03_gold.g_trppu_entite".

Les informations des objets/produits sont dans une table dimension "ppd_dd_kairos_int.03_gold.g_trppu_obj_mapping" qui contient le mapping entre les codes TRPPU et les codes comptages de CTR utilisés pour TRPPU.

Une table "ppd_dd_kairos_int.02_silver.s_commun_calendrier_jour"" est partagée dans le catalogue "Kairos" et peut être utilisé pour récupérer des informations liées aux dates si nécessaire comme les fériés, l'année, le mois, le n° du jour dans la semaine etc.....

Les tables golds restent agrégées selon une temporalité, une agrégée à la journée, une au mois et une à la semaine.

Chacune d'elle contient les trafics des sites pour tous les objets TRPPU.

La table "g_trppu_trafics_jour" est partitionnée à l'année et au mois et triée sur le code regate et la date, ainsi une requête sur cette table sera "optimisée" en utilisant dans la clause where le code de l'année et le mois correspondant aux dates pour effectuer les recherches.

Sur le même principe, la table "g_trppu_trafics_semaine" est partitionnée sur le "co_annee_comptage" et triée sur le code regate et le co_semaine_comptage.

La table "g_trppu_trafics_mois" est partitionnée sur le "co_annee_comtage" et triée sur le code regate et le co_mois_comptage.

Quelle que soit la table dans laquelle les données sont récupérées, la recherche se fait toujours pour un code regate, une date de début et une date de fin. Selon la table accédée, il faut utiliser dans les clauses where soit le code de l'année et le mois des dates de début et de fin, soit le code de l'année et le code de la semaine. Ces informations peuvent être soit recalculées à partir des dates en paramètre soit récupérées de la table calendrier citée ci-dessus. 

tous les trafics compris dans la plage de date en paramètres sont à récupérés pour le site et le résultat est agrégé à l'objet/produit.




Les tables à partir desquelles les informations sont récupérées sont : 

g_trppu_trafics_jour
g_trppu_trafics_mois
g_trppu_trafics_semaine




Dans ces tables les informations de trafics à récupérer sont : 

l'objet/produit
le trafic retenu correspondant à l'information "trafic constaté" (dans les tables bronze :  "nb_objet_retenu" (trafic brut))
le trafic prévisionnel correspondant à l'information "trafic prévu" (dans les tables bronze :  "nb_objet_prevu_recadre_bu"  )




Filtrage des données dans la requête sql :

Les dates de la période sont à rechercher sur les champs :
"da_comptage" pour la table agrégée à la journée.
"co_semaine_comptage" pour la table agrégée à la semaine.  format : "AAAA-NS"  (NS= n° de la semaine, exemple : 2026-12 pour la 12ème semaine de l'année)
"co_mois_comptage" pour la table agrégée aux mois. format "AAAA-MOIS" (exemple : 2026-03 pour mars 2026)
=> Selon la table interrogée, le format des dates de la période sont à adapter par rapport au format utilisé dans la table requêtée.
=> Pour rappel :
ces "dates" sont celles qui doivent être comparées à la date pivot qu'il faut donc adapter au bon format.
le trafic à récupérer avant la date pivot est le trafic constaté
le trafic à récupérer à partir de la date pivot est le trafic prévisionnel
Le code regate du site correspond au champ "co_regate" dans les tables.

Critères d'acceptance :

appeler l'API "Databricks" avec différent paramètres et vérifier son comportement et les informations retournées :

avec juste un code regate  => doit retourner le fait qu'il manque les paramètres de la période et rappeler les paramètres
avec juste une période => doit retourner le fait qu'il manque le paramètre régate et rappeler les paramètres
avec juste une date de début => doit retourner le fait qu'il manque des paramètres et rappeler les paramètres
avec juste une date de fin => doit retourner le fait qu'il manque des paramètres et rappeler les paramètres
avec juste une date pivot => doit retourner le fait qu'il manque des paramètres et rappeler les paramètres
avec code regate, date de début, la date de fin et la date pivot pour une période de plus de 2 ans sur le passée => doit retourner le fait que la période dépasse les 2 ans d'interrogation permis et rappeler les paramètres
avec code regate, date de début, date de fin et date pivot pour une période de 2 ans dans le passée => doit retourner le trafics pour le site sur la période demandée avec du trafic constaté et prévisionnel
avec code regate, date de début, date de fin et date pivot pour une période de 2 ans incluant du passée et du futur => doit retourner le trafics pour le site sur la période demandée avec du trafic constaté et prévisionnel
avec code regate, date de début, date de fin et date pivot pour une période de 2 ans dans le futur => doit retourner le trafics pour le site sur la période demandée avec juste du trafic prévisionnel
vérifier que le retour obtenu correspond bien à une "ligne par objet et un nombre correspondant à la somme des trafics pour l'objet concerné"
faire une requête en base pour vérifier que le résultat est correcte aussi bien en trafics qu'en objets renvoyés.
vérifier avec la requête en base pour les 3 cas les trafics réels et prévisionnels pour valider les résultats
