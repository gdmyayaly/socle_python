Objectif

Définir les règles de construction, d'organisation et de livraison des scripts de mise à jour de base de données utilisés par le batch de déploiement MD01.

L'objectif est de garantir que toute évolution de schéma ou initialisation de données soit déployable de manière automatique, reproductible et traçable via le batch de mise à jour de base de données.

User Story

En tant que développeur TRPPU

Je souhaite livrer les scripts SQL, procédures et fichiers d'initialisation selon une organisation standardisée

Afin de permettre au batch dsr_trppu_maj_bd.py du module MD01 de déployer automatiquement les évolutions de base de données dans l'ordre attendu.

Contexte

Le batch de mise à jour de base de données dsr_trppu_maj_bd.py déployé dans le module MD01 exécute les évolutions de schéma à partir d'un répertoire de version.

Chaque livraison doit contenir l'ensemble des scripts nécessaires à l'installation ou à la mise à jour de la version concernée.

Le batch n'embarque aucune connaissance fonctionnelle du contenu des mises à jour.

Il s'appuie exclusivement sur :

l'arborescence de livraison ;
le fichier de configuration de la version ;
les scripts et fichiers livrés.
Principe général

Pour chaque mise à jour :

 
TRPPU_Vx.y.z
 

les développeurs doivent :

créer les scripts nécessaires ;
les déposer dans les répertoires appropriés ;
définir leur ordre d'exécution ;
fournir les éventuels fichiers d'initialisation ;
fournir les scripts de retour arrière.

Règles de construction des scripts
Un objet = un script

Chaque objet de base de données doit être livré dans un script dédié.

Exemples :

Création d'une table

 
001_create_trppu_import_cles.sql
 

Création d'un index

 
001_idx_import_cles.sql
``
 

Création d'une vue

 
001_create_vue_trafic_site.sql
 

Création d'une procédure

 
001_create_proc_yb07.sql
 

Évolution d'un objet

Une modification d'objet doit être livrée dans un script dédié.

Exemple :

 
003_alter_trppu_version_cle_add_date_fin_validite.sql
 

Initialisation des données

Les données d'initialisation doivent être fournies dans des fichiers distincts.

Exemple

 
referentiel.csv
 
parametres.csv
 

ou

 
001_init_referentiel.sql
 

selon la stratégie retenue.

Organisation des répertoires

Les objets doivent être déposés dans le répertoire correspondant à leur nature.

Tables

 
tables
 

Vues

 
vues
 

Procédures

 
procedures
 

Contraintes

 
contraintes
 

Index

 
index
 

Données

 
data

Pour rappel, les données sont à déposer sous /dsr/dsradmaa/donnees/trppu
 

Rollback

 
rollback
 

Ordonnancement

L'ordre d'exécution est piloté par :

 
trppu_vX.Y.Z.yml
 

Exemple

 
version: TRPPU_V1.2.0
 
execution_order:

tables
vues
procedures
contraintes
index
data
 
rollback_order:
rollback




Numérotation des scripts

À l'intérieur d'un répertoire, les scripts doivent être numérotés afin de garantir leur ordre d'exécution.

Exemple

 
001_create_table.sql
 
002_create_table.sql
 
003_alter_table.sql
 

Rollback obligatoire

Toute évolution de schéma doit disposer d'un mécanisme de retour arrière.

Les scripts associés doivent être présents dans :

 
rollback
 

Exemple

Création :

 
001_create_table.sql
 
002_create_index.sql
 

Rollback :

 
001_drop_index.sql
 
002_drop_table.sql

Règles de gestion
RG-001

Chaque objet de base de données doit être livré dans un script dédié.

RG-002

Les scripts doivent être déposés dans le répertoire correspondant à leur type.

RG-003

Les scripts d'une même catégorie doivent être numérotés.

RG-004

Toute évolution doit disposer d'un rollback.

RG-005

Les données d'initialisation doivent être livrées séparément des scripts de création d'objets.

RG-006

Le fichier de configuration de version constitue la référence d'exécution utilisée par MD01.

RG-007

Aucune intervention manuelle en base ne doit être nécessaire après la livraison.

Critères d'acceptation
CA-01

Étant donné une nouvelle version TRPPU

Quand les scripts sont livrés

Alors chaque objet est présent dans un fichier distinct.

CA-02

Quand la structure de livraison est analysée

Alors les scripts sont présents dans les bons répertoires.

CA-03

Quand MD01 exécute la version

Alors les scripts sont exécutés dans l'ordre défini dans le fichier YAML.

CA-04

Quand une demande de rollback est réalisée

Alors les scripts présents dans le répertoire rollback permettent de restaurer l'état précédent.

CA-05

Quand la livraison est déposée dans le dépôt MD01

Alors elle contient l'ensemble des scripts, procédures, données et fichiers de configuration nécessaires à un déploiement totalement automatisé.

Résultat attendu

À l'issue de cette US, chaque livraison de base de données TRPPU :

est autoportée ;
est entièrement exécutable par le batch dsr_trppu_maj_bd.py ;
est totalement traçable ;
est rollbackable ;
respecte une organisation standard commune à l'ensemble des futures versions du projet.
