En tant que TRPPU

Je souhaite dupliquer un scénario existant

Afin de disposer rapidement d'une copie complète sur laquelle effectuer de nouvelles simulations sans modifier le scénario d'origine.
 

L'application doit permettre à un utilisateur de créer un nouveau scénario à partir d'un scénario existant. Le nouveau scénario doit constituer une copie complète du scénario source afin que les utilisateurs puissent réaliser des variantes sans repartir d'une configuration vierge.

La duplication doit concerner non seulement la fiche scénario mais également toutes les données métier qui lui sont rattachées :

TMH
Variations des trafics prévisionnels
Périodes neutralisées
Paramétrages PIC
Coefficients PIC
Toute autre donnée spécifique enregistrée pour le scénario.
 
Principe général

Le service de duplication agit comme un service orchestrateur.

Son rôle n'est pas de réaliser lui-même tous les traitements métier mais de piloter les services existants afin de :

récupérer les données du scénario source ;
créer le nouveau scénario ;
dupliquer progressivement toutes les données liées ;
rattacher ces données au nouvel identifiant de scénario ;
garantir que le scénario d'origine reste totalement inchangé.
 
Entrées du service
Paramètre obligatoire

idScenarioSource




Paramètres calculés

Le service génère automatiquement :

un nouvel identifiant scénario ;
un nouveau libellé ;
les informations de création (date, utilisateur...).
 
Étape 1 - Création du nouveau scénario

Le service crée une nouvelle ligne dans la table SCENARIO trppu_scenario :

Données reprises
site, code regate ;
date de début, de fin et date pivot ;
paramètres généraux :
périodes réalisé début et fin, périodes prévisionnel début et fin
nombre de jour de la semaine, nombre de jour ouvrés et ouvrables, nombre de jour du scénario
indicateurs :
id_pic_version
Données modifiées
nouvel ID scénario
nouveau libellé de scénario.
statut : "en cours"
date de création : date du jour
date de validation : vide/null
date de mise en prod : vide/null
booléen est_fige à 0
date de mise à jour : date du jour (modifier à chaque update de la ligne)
id_rh (création et mise à jour) : id_rh de l'utilisateur qui a dupliqué / créer le scénario
trafic_pdi_calculé : 0
trafic_agrebal_calculé : 0
 
Étape 2 - Duplication des TMH dans trppu_tmh

Objectif
Créer pour le nouveau scénario l'ensemble des données TMH existantes sur le scénario source.

Le service :

récupère les TMH du scénario source ;
crée les nouvelles lignes ;
remplace l'ID scénario par le nouvel identifiant ;
enregistre les données.
Traitement
2.1 Chargement des données source

Le service appelle les mécanismes existants utilisés lors de l'édition d'un scénario afin de récupérer :

les TMH calculés ;
les TMH éventuellement modifiés ;
les informations associées au scénario source.
2.2 Constitution du référentiel cible

Pour chaque enregistrement récupéré :

création d'un nouvel objet métier ;
remplacement de l'identifiant du scénario source par l'identifiant du nouveau scénario pour les nouvelles lignes ;
conservation des autres données métier.
2.3 Persistance

Les services de sauvegarde existants sont appelés afin d'enregistrer :
 
 
TMH Source (Scénario A)
↓
Transformation
↓
TMH Copie (Scénario B)
 
Le scénario source n'est jamais mis à jour.

Contrôle

Vérifier que :

le nombre de TMH dupliqués est identique ;
toutes les nouvelles lignes sont rattachées au nouvel ID scénario ;
aucune ligne n'est écrasée/modifiée sur le scénario source
 
Étape 3 – Duplication des périodes neutralisées
Objectif

Reproduire toutes les périodes neutralisées éventuellement définies par l'utilisateur.

Traitement
3.1 Lecture

Récupération des périodes neutralisées associées au scénario source. 

3.2 Duplication

Pour chaque période :

création d'un nouvel enregistrement ;
conservation des dates ;
conservation du motif ou du type ;
affectation du nouvel identifiant scénario pour les nouvelles lignes.
3.3 Sauvegarde

Appel des services de persistance existants.

Période Noël
Scénario A
        ↓
Duplication
        ↓
Période Noël
Scénario B
 

Contrôle

L'utilisateur doit retrouver exactement les mêmes périodes neutralisées dans le scénario cloné.




Étape 4 – Duplication des variations de trafic prévisionnel
Objectif

Conserver les ajustements réalisés par l'utilisateur sur les trafics prévisionnels.

Traitement
4.1 Chargement

Récupération des valeurs spécifiques enregistrées dans la table de variation du prévisionnel. 

4.2 Duplication

Pour chaque variation :

conservation du trafic concerné ;
conservation du pourcentage ou du coefficient appliqué ;
remplacement de l'ID scénario. 
4.3 Sauvegarde

Persistance des nouvelles lignes pour le nouveau scénario.

Exemple

Scénario source
Courrier : +4 %
IP : -6 %
↓
Scénario dupliqué
Courrier : +4 %
IP : -6 %
 
L'utilisateur repart du même contexte métier que celui du scénario d'origine.
 

Étape 5 – Duplication des paramètres PIC
Objectif

Reprendre les personnalisations de configuration PIC éventuellement réalisées.

Principe

La duplication ne doit porter que sur les données réellement personnalisées.

Les valeurs standard fournies par défaut ne doivent pas être dupliquées inutilement.

Traitement
Cas n°1 : aucune personnalisation

Aucune ligne spécifique trouvée.

Action :

Aucune donnée à créer

Le nouveau scénario utilisera automatiquement les paramètres de référence.

Cas n°2 : présence de personnalisations

Pour chaque paramètre personnalisé :

récupération de la valeur ;
création d'un nouvel enregistrement ;
rattachement au nouvel ID scénario.
Contrôle

Dans l'IHM, les paramètres apparaissant aujourd'hui comme des valeurs modifiées (ex. affichage en rouge) doivent apparaître de manière identique après la duplication.




Étape 6- Contrôle d'intégrité

Le service vérifie :

présence du scénario ;
présence des données dupliquées ;
cohérence des rattachements ;
absence de référence restante vers l'ancien scénario.
Étape 7- Retour du service (exemple)




Retour :

Points de vigilance
Isolation des scénarios

Après duplication :

toute modification future doit impacter uniquement le nouveau scénario ;
aucune mise à jour ne doit être réalisée sur le scénario source.
 
Critères d'acceptation
CA1

Étant donné un scénario existant, lorsqu'un utilisateur demande sa duplication, alors un nouveau scénario est créé avec un nouvel identifiant.

CA2

Toutes les données métier associées sont reproduites dans le nouveau scénario.

CA3

Les données du scénario source ne sont jamais modifiées.

CA4

Le nouveau scénario est immédiatement éditable dans toutes les IHM existantes.

CA5

Toute modification réalisée après duplication n'impacte que le scénario dupliqué.

CA6

En cas d'erreur pendant la duplication, aucune donnée partiellement créée ne doit être conservée (rollback transactionnel).
