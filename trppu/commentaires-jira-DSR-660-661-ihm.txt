COMMENTAIRE JIRA — DSR-660 (Intégration IHM : lecture du paramétrage PIC)
================================================================================

*Intégration IHM terminée* — composant "Configuration PIC" (module TRPPU,
composant `configpic`) branché sur le service YS04.

*Appel réalisé par l'IHM*
GET {trppuApiUrl}/scenarios/{id_scenario}/pic-coefficients?id_session_ihm={uuid}

- `id_scenario` : récupéré du contexte applicatif (scénario en cours, localStorage) ;
- `id_session_ihm` : UUID de session généré/persisté par l'IHM et transmis
  systématiquement en query param pour la traçabilité Kibana (exigence du ticket).

*Traitement de la réponse côté IHM*
- L'enveloppe renvoyée par le service est consommée intégralement :
  `id_pic_version_defaut`, `id_pic_version_scenario` (null si le scénario n'a
  jamais été surchargé), `niveau_scenario`, `coefficients[]`.
- Les jours renvoyés par l'API (LUNDI…SAMEDI) sont convertis vers les codes
  d'affichage IHM (LUN…SAM) via une table de correspondance.
- Le tableau est reconstruit par produit (OO, OS, PRESSE, COLIS, PPI, IP) ×
  jour × densité (0 = dense, 1 = clairsemée, 2 = clairsemée2) ; le samedi
  n'affiche que la densité 0 conformément à la maquette.
- Distinction visuelle des valeurs modifiées : chaque cellule porte
  l'`id_pic_version` renvoyé ligne à ligne par le service. Si
  `id_pic_version != 1` (version par défaut nationale), la cellule est affichée
  en gras/vert = coefficient propre au scénario. C'est bien le champ
  `id_pic_version` qui pilote la distinction, comme demandé dans le ticket
  (le flag `modifie` du service est disponible en complément).
- Les coefficients sont affichés en format français (virgule + suffixe "%").

*Cas particuliers gérés*
- Aucun scénario en cours (pas d'id_scenario dans le contexte) : aucun appel
  réseau, tableau vide + message "Aucun scénario en cours : paramétrage PIC
  indisponible" (le service exige un scénario existant).
- 404 (scénario introuvable) : message dédié "Scénario introuvable :
  paramétrage PIC indisponible."
- Autre erreur : message générique "Erreur de chargement du paramétrage PIC."

*Reste à valider (côté PO / environnement connecté)*
- Échelle du coefficient : l'IHM affiche et transmet des pourcentages (ex. 21.7).
  À confronter aux données par défaut (id_pic_version = 1) en base ; si la base
  stocke des fractions (ex. 0.8500), une conversion x100 / /100 sera ajoutée
  dans le service IHM uniquement (aucun impact composant ni backend).
- Ligne "total trafic" : règle de gestion métier à définir (placeholder =
  moyenne des coefficients de la colonne).

COMMENTAIRE JIRA — DSR-661 (Intégration IHM : enregistrement d'un coefficient)
================================================================================

*Intégration IHM terminée* — sauvegarde automatique d'un coefficient modifié
depuis le tableau "Configuration PIC", déclenchée à la perte de focus (blur)
d'une cellule éditée.

*Appel réalisé par l'IHM*
PUT {trppuApiUrl}/scenarios/{id_scenario}/pic-coefficients?id_session_ihm={uuid}
Body JSON :
{
  "co_produit":   "OO",        // code produit de la ligne éditée
  "jour_semaine": "LUNDI",     // converti du code IHM (LUN) vers le format API
  "densite":      0,           // 0 = dense, 1 = clairsemée, 2 = clairsemée2
  "coef":         21.7,        // valeur saisie (voir contrôles ci-dessous)
  "id_rh":        "A123456"    // identifiant RH de l'utilisateur connecté
}

Conformité au contrat du service :
- `id_scenario` est transmis dans l'URL et non dans le body (le service rejette
  tout champ non prévu — extra=forbid) ;
- `id_rh` est obligatoire : il est lu depuis le contexte applicatif (posé à la
  connexion). S'il est absent, AUCUN appel n'est émis et l'IHM affiche
  "Identifiant RH inconnu : modification impossible (reconnectez-vous)" ;
- `id_session_ihm` transmis en query param sur chaque appel (traçabilité).

*Contrôles de saisie côté IHM (avant tout appel au service)*
1. À la frappe : seuls sont acceptés les chiffres, UN seul séparateur décimal
   (point "." ou virgule "," indifféremment : 21.7 = 21,7) et 4 décimales
   maximum (aligné sur le type DECIMAL(7,4) du backend). Tout autre caractère
   (lettres, signe, %, second séparateur, 5e décimale) est ignoré/supprimé
   automatiquement. Longueur max de saisie : 8 caractères (ex. "100,0000").
2. À la perte de focus : la valeur doit être un décimal compris entre 0 et 100,
   sinon la cellule passe en erreur avec le message "Veuillez saisir une valeur
   décimale comprise entre 0 et 100." et rien n'est envoyé.
3. Champ vidé : restauration de la valeur précédente, aucun appel.
4. Valeur inchangée : simple renormalisation de l'affichage, aucun appel.

*Comportement pendant et après l'enregistrement*
- Pendant l'appel : la cellule passe en gras/rouge ("enregistrement en cours"),
  les totaux sont recalculés immédiatement.
- Succès : la cellule prend l'`id_pic_version` RENVOYÉ par le service dans la
  réponse ({action, id_pic_version}) — pas de valeur codée en dur — et s'affiche
  donc en gras/vert (coefficient propre au scénario). Les trois actions
  possibles du service (update / insert_coef / insert_version_and_coef) sont
  transparentes pour l'utilisateur.
- Échec : la valeur PRÉCÉDENTE est restaurée dans la cellule (pas d'affichage
  d'une valeur non persistée), les totaux sont recalculés, et un message
  contextualisé est affiché :
    . 409 -> "Scénario figé ou non modifiable : coefficient non enregistré."
    . 422 -> "Paramètre invalide : coefficient non enregistré."
    . 404 -> "Scénario introuvable : coefficient non enregistré."
    . autre -> "Erreur lors de l'enregistrement du coefficient."

*Édition autorisée uniquement si*
- un scénario est en cours (sinon tableau en lecture seule) ;
- la cellule correspond à une combinaison produit/jour/densité existante
  (les cellules vides ne sont pas éditables).

*Vérifications effectuées*
- Contrat validé contre les schémas Pydantic du service : body accepté pour les
  6 jours mappés ; `id_scenario` dans le body bien rejeté (justifie son passage
  dans l'URL) ; coefficient négatif rejeté ; enveloppe de lecture conforme.
- Logique de contrôle de saisie validée sur 11 cas (21.7 / 21,7 acceptés,
  "abc" vidé, "1.2.3" -> "1.23", troncature à 4 décimales, "-" et "%" ignorés).

*Reste à valider (côté PO / environnement connecté)*
- Échelle du coefficient (pourcentage vs fraction) — voir commentaire DSR-660.
- L'application hôte doit alimenter l'identifiant RH dans le contexte IHM à la
  connexion de l'utilisateur (setIdRh), le service YS04 le chiffrant côté
  serveur avant stockage.
